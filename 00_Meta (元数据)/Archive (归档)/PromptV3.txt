三、第一份：完整中文翻译（Translation）

逐句、完整、等义地翻译论文标题、摘要、关键词、正文全部章节、公式、图题图注、表格、脚注和论文正文内的附录。保留限定词、括号内容、公式编号及正文引用编号，不概括、删减、合并或擅自补写。作者、机构、邮箱、版权信息、页眉页脚、致谢和文末参考文献列表可以去除。

如果另附独立 Supplementary，不必全文翻译，只需在 Translation 中简要交代它包含哪些内容；其中有助于理解核心方法的技术细节，可以在论文笔记或工程笔记中引用。

图片优先复用现有 Obsidian 图片链接，并原样保留。缺失图片时，从 PDF 中完整提取并放到仓库现有资源目录。注意图的边缘、标注、图例及各个分图不要截断，宁可保留一点外边距。图表放在对应的完整段落后，不要打断正文。图题和图注完整翻译，图注后加入简短客观的「图片内容解释」。表格转为完整 Markdown 表格，保留全部数据、单位、脚注和原有强调。

公式保留原本的符号、运算关系和编号：行内 `$...$`，独立公式 `$$...$$`，原文有编号时保留 `\tag{n}`。公式块、表格与正文之间适当空行，保证 Obsidian 正常渲染。

`Translation.md` 只包含忠实翻译和客观图片解释，不加入个人理解、代码分析或额外推导。

四、第二份：论文精读笔记（paper_notes）

这份笔记必须以已经完成的 Translation 为底稿，而不是把论文重新概括成一篇新文章。

从标题、摘要、Introduction、Related Work 到 Method / Approach / Framework 结束，完整复制 Translation 中相应的译文、公式、图表与章节顺序，不改写、删减或移动原文段落。只在相关完整段落、公式或图表之后插入理解性 note。

Method 之后的 Experiments、Discussion、Conclusion 和 Appendix 可以选择主要结果、重要消融与讨论。被选中的原文段落仍应保持 Translation 中的译文内容；全文保留在 Translation。

文件开头提供论文网址、本地 PDF 链接、相关基础笔记的 Obsidian 双链和符合现有仓库习惯的 YAML Frontmatter，例如：

---
type: paper-note
tags: [cv, semantic-segmentation, ...]
status: in-progress
model: 方法名
venue: 会议或期刊简称加年份
---

尽量复用仓库里已有的 tags，不必每篇创造一套新标签。如果拿到的是 arXiv 版本，请查询是否已正式发表；尚未确认时如实写 arXiv。

所有理解性内容使用：

> [!note] 我的理解｜具体而清楚的标题
> 用自己的话讲明白机制、作用、公式或必要的技术细节。

精读重点仍是 Method：

- 在总体框架图后，用容易理解的语言说明输入、监督信号、各模块如何串起来、中间输出交给谁、最终预测或伪标签怎样产生，以及训练与推理的主要区别。
- 对每个核心模块，先讲「它实际上在处理什么数据、做了什么操作、解决什么问题」，再解释论文中的公式和设计理由。
- 关键公式按照「整体含义 → 主要符号与运算 → 必要的形状 → 参数作用 → 简单例子」解释。不要刚开始就堆很多矩阵和梯度。
- 如果方法涉及多个 loss、冻结模型、教师学生或伪标签，用「谁监督谁、哪些部分在学习」的通俗流程说明，再补充确有必要的梯度信息。
- Introduction 与 Related Work 的 note 主要解释动机、必要背景和与已有工作的区别，充分但不逐段重复。论文笔记的重心是读懂作者思想，而不是提前展开源码细节。

如果论文与实际代码存在会影响方法理解的重要区别，可在对应 note 中简要说明。一般的 PyTorch 写法和完整的张量变化，留到第三份工程笔记。

五、第三份：围绕 Method 的工程源码学习笔记（code_notes）

**这份笔记的定位不是项目开发手册、完整复现教程，也不是工程审计，而是「把论文 Method 变成看得懂、学得会、以后能借鉴的 PyTorch 实现」。**

请寻找作者官方仓库或来源可靠的公开实现，真正打开核心源码阅读，而不是只看 README 或根据论文推断。开头保留论文与仓库链接，以及所分析的关键源码文件链接即可；不必专门统计配置、超参数、项目目录、实验运行命令或 commit 信息。

### 1. 先建立模型和代码的对应关系

先用一段通俗的话说明论文核心思路在代码中是怎样落地的，核心模块分别做什么。随后用简单的数据流把 Method 串起来，例如：

图像 / 文本等输入 → Backbone 特征 → 作者提出的模块 A → 模块 B → 输出结果。

如果论文有离线建库、特征提取、教师生成伪标签等关键步骤，并且它们属于方法本身，也要说明它们如何与主体模块连接。但不需要顺带分析整个数据加载、优化、验证和部署流程。

找出实现这些核心步骤的类、函数及调用关系，让我知道从哪份源码开始阅读、每个函数在方法中处于什么位置。**能把 Method 走通就够了，不需要逐个读完整个仓库。**

### 2. 重点讲清核心模块的代码逻辑

对论文真正重要或写法很有学习价值的模块，适当引用源码中的关键片段，结合论文解释：

- 这一段代码具体想完成什么操作，为什么这么设计？
- 输入是什么，经过了哪些关键计算，输出给了谁？
- 这里调用的 PyTorch 函数、索引、广播、归一化或矩阵运算具体是怎样工作的？
- 哪些是作者专门提出的设计，哪些是其他模型也可以复用的常见工程手法？
- 论文公式在代码里是怎样对应起来的？如果有重要的实现差异，也解释清楚。

讲解顺序建议为：**一句大白话直觉 → 关键源码片段 → 分步骤解释代码 → 必要的张量变化 → 这一写法值得学在哪里。**

这里希望分析得充实一些，而不是只列函数名或把论文 Method 换种说法。尤其是 Attention 的修改、特征提取与融合、Query / Key / Value、原型构建、空间信息交互、Decoder 等有代表性的计算逻辑，可以写得更深入。对于不熟悉的 PyTorch API，顺手讲一下它的用途和关键参数，让我不仅理解作者的模型，也学到自己写代码的方法。

不需要逐行解释所有源码，也不要求复制完整函数。优先选那些真正承载方法思想的几段计算；普通包装代码、路径处理和日志等可以略过。引用源码时附文件路径和对应链接，方便以后直接回看。

### 3. 张量分析要细，但只围绕真正关键的计算

对影响 Method 理解的主要步骤，说明实际的 tensor shape 怎样变化，以及这些变化为什么有意义。例如：

- `B, N, C, D, H, W` 等维度分别表示什么；
- `reshape`、`flatten`、`permute`、`transpose`、`concat` 等怎样组织数据；
- `matmul`、`einsum`、Attention、相似度、池化、`topk`、`gather`、`softmax` 等实际作用在哪些维度；
- patch/token 特征怎样交互，又如何变成特征图、CAM、mask 或预测结果；
- 若涉及不同网络的特征融合，维度和特征空间如何对齐。

不要仅用一张 shape 表就结束。尽量把 **「这一行代码做了什么 → shape 如何变 → 数值代表什么 → 为什么这样处理」** 联系起来说明。

既要有抽象写法（如 `[B,N,D] → [B,N,C]`），也可以举一个容易算懂的具体数字例子；例子用于帮助理解，不要求调查作者全部实验配置。对于简单的 `reshape` 或已经很清楚的步骤不用机械扩写，遇到容易绕晕的矩阵乘法、索引、Attention 和跨模块融合时多解释一些。

### 4. 学习怎样把这些写法用到自己的模型里

这是工程笔记很重要的一部分。每讲完一个有代表性的模块，尽量提炼出它背后通用的实现方法，例如：

- 一种 Attention 或 Affinity 的构造与修改方式；
- 一种特征对齐、聚合、融合或残差连接写法；
- 一种通过 mask 取区域特征、构造原型或进行检索的方法；
- 一种 Query / Decoder 的组织方式；
- 一种把 token 重新排列成空间预测的做法。

告诉我这个写法的关键输入输出、依赖什么前提，以及换到另一个模型时通常需要改动哪些部分。必要时可提供一小段**简化的可复用 PyTorch 示例**，与作者原始源码分开标注，帮助我以后复制思路、修改自己的模型。

如果某个 loss、`detach`、`no_grad` 或训练/推理分支对核心方法的运作至关重要，也应解释；但不需要为了覆盖训练流程而逐项检查优化器、学习率、训练轮数或完整评估流程。

末尾用一个自然的总结归纳本篇最值得学会的几个实现思路、对应源码入口和适用场景。重点不是它的实验配置或跑分，而是**读完后我学会了什么代码逻辑、将来可以怎样借鉴。**
