## 三、推荐笔记结构

请根据算子特点自然调整，但至少包含以下内容。

### 1. 本页定位

用一段简短说明解释：

- 这个页面整理什么；
- 当前资料来自哪些研究方向；
- 它与单篇论文笔记有什么区别。

### 2. 这个算子解决什么问题

先用大白话解释，再给出专业表述。

需要说明：

- 模型中出现了什么具体现象；
- 为什么会出现；
- 这个算子在数据流的哪个位置发挥作用；
- 哪些相似现象其实不是这个算子负责解决的。

可以加入：

> [!note] 我的理解｜……

用于区分论文叙事、直观理解和实际机制。

### 3. 统一输入输出张量

明确写出：

- 输入张量；
- 输出张量；
- 每个符号和维度的含义；
- 必须满足的尺寸或特征空间条件；
- reshape、permute、concat、projection、interpolate等中间变化。

不能只写公式。**每一个展示公式**（包括 shape 声明、损失、归一化、分段规则、总结框公式）结束后，必须紧邻加入统一格式：

**公式解释：** ……

不是只解释“关键公式”，也不能把多个相隔的公式留到章节末尾统一解释。若两个公式分别使用两个 `$$...$$` 块，则每个公式块后都要有自己的解释。解释至少回答：

1. 公式在计算什么；
2. 每个矩阵或张量代表什么；
3. 哪两个维度参与运算；
4. 哪个维度被消去；
5. 输出 shape 是什么；
6. 输出的每个元素表示什么；
7. 如果没有矩阵乘法或维度消去，也要明确写出“这里只声明输入”“这里只逐元素运算”或“没有维度被消去”；
8. 如果是 softmax、max、mean、sum、归一化或插值，要明确操作发生在哪个维度。

例如写出：

S = P_hat T_hat^T ∈ R^{B×N×C}

之后，还需要解释：

- P_hat 是 `[B,N,D]`；
- T_hat^T 是 `[D,C]`；
- 矩阵乘法消去特征维 D；
- S[b,n,c] 表示第 b 张图的第 n 个视觉单元与类别 c 的匹配程度。

至少给出一个具体数字例子，例如：

[B,N,D] = [2,400,512]
[D,C] = [512,20]
输出 = [2,400,20]

并解释具体元素，例如：`S[0,17,3]` 表示第 1 张图第 18 个视觉单元与第 4 个类别的匹配分数。

如果需要恢复二维空间，完整解释：

[B,N,C]
→ permute
→ [B,C,N]
→ reshape
→ [B,C,H',W']
→ 上采样
→ [B,C,H,W]

说明双线性插值、最近邻插值、转置卷积等方法的区别；如果涉及跳跃连接，也要说明它在什么时候出现，而不是一句“上采样后得到结果”直接跳过。

还要明确：

- 双线性插值适合连续特征、logit、概率或 CAM；
- 最近邻插值适合离散类别索引，避免产生不存在的类别编号；
- 转置卷积包含可学习参数，不应与无参数 resize 混为一谈；
- `reshape/view` 是否要求连续内存和正确的 token 顺序；
- `permute` 只是换轴，不进行数值混合；
- 广播具体把哪个长度为 1 的维度扩展到什么 shape。

优先链接现有基础笔记，例如：

[[downsampling_and_upsampling(下采样与上采样)]]

### 4. 代表论文逐篇说明

先建立一张具体的论文表格。至少包含：

| 论文 | 任务与起点 | 原方法存在的问题 | 具体做法 | 与当前算子的关系 |
|---|---|---|---|---|

“具体做法”不能只写模块名称。

错误示例：

“使用TSA和VCE改善对齐。”

正确示例：

“从扩散模型提取patch间空间亲和力并注入CLIP后几层注意力；同时使用扩散模型生成的单类图像构建视觉键值缓存，让真实图像patch查询多种类别外观。”

如果出现ISA、TSA、VCE、CMPA等缩写，第一次出现时必须说明：

- 英文全称；
- 中文含义；
- 输入；
- 输出；
- 是否可学习；
- 在整个数据流中负责什么。

不能默认读者记得某篇论文中的模块名称。

代表论文表格之后，还应挑出最重要的论文分别补充一小段说明，尤其解释：

- 监督信号从哪里来；
- 模块插在整条数据流的哪个位置；
- 它主要修复语义问题、空间问题、优化问题还是效率问题；
- 它与其他论文使用的是同一形式，还是只是名称相似；
- 论文声称的机制是否能从公式或代码中得到支持。

不要只写两三篇论文后就快速结束；只要指定目录中有直接相关且内容可靠的论文，就应形成足够具体的横向比较。

### 5. 常见实现形式归纳

在论文表格之后，再把具体论文抽象为若干实现形式，例如：

- 全局图文匹配 + 梯度定位；
- patch—text直接对齐；
- region—text对齐；
- 原型对齐；
- 特征空间映射；
- 检索式对齐。

建立对比表：

| 实现形式 | 输入单元 | 是否训练 | 优点 | 局限 | 代表论文 |
|---|---|---|---|---|---|

说明这些形式：

- 有什么共同点；
- 主要区别是什么；
- 能否组合使用；
- 哪些论文实际同时使用了多种形式。

### 6. 各种实现怎样工作

每种实现形式都按照以下顺序解释：

1. 大白话直觉；
2. 数据流；
3. 数学公式；
4. 公式逐项解释；
5. 输入输出张量；
6. 适用场景；
7. 局限和容易误解的地方；
8. 对应论文双链。

不要连续堆叠公式。公式和公式之间必须有语言说明。

如果内容比较难，优先把最简单的前向流程讲清楚，再增加专业术语和数学表达。

### 7. 一个官方仓库的代码分析

只选择一个最有代表性的开源仓库，优先选择重点论文的官方代码。

静态追踪一条与当前算子直接相关的调用链，例如：

输入
→ 特征提取
→ 算子函数
→ 相似度或融合
→ reshape/upsample
→ 输出或损失

需要记录：

- 仓库地址；
- 阅读时使用的commit；
- 文件路径；
- 类或函数名称；
- 准确的GitHub源码行链接；
- 调用关系；
- 输入输出shape；
- 哪些参数会训练；
- 哪些结果会detach；
- 论文公式与代码实现的差异。

固定版本要求：

- 必须记录完整 commit hash，不只写分支名、短 hash 或 `main`；
- GitHub 文件链接必须固定到该 commit，并尽量精确到源码行；
- 如果仓库不可访问，明确写“未能完成源码核对”，不得根据论文公式伪造路径、函数和 shape；
- 如果仓库能访问，要实际阅读相关文件，不能只根据函数名或 README 推断实现。

只保留理解算子所需的关键代码片段，不要复制整个文件。

代码后必须逐行或分步骤解释。例如：

- 为什么要reshape；
- 广播后产生什么shape；
- softmax在哪个维度；
- min-max在哪个维度；
- 为什么去掉CLS token；
- 怎样恢复空间维度；
- 背景分支怎样抑制前景；
- 缓存键和值怎样初始化线性层。

同时指出值得注意的工程细节，例如：

- 归一化维度是否符合常见写法；
- 除法是否缺少epsilon；
- 论文中的余弦相似度是否被代码扩展成其他计算；
- 构造参数与forward实际使用是否一致；
- 某些中间结果是否被无效计算；
- 论文与代码对背景含义是否存在差异。

还应检查：

- 构造函数参数是否真的在 `forward` 中使用；
- `train()`、`eval()`、`requires_grad`、优化器参数组、`no_grad()` 和 `detach()` 分别控制什么；
- 代码中的候选选择是动态 `argmax`，还是固定索引却使用了容易误解的变量名；
- 背景、unknown、ignore、no-object 的通道顺序和整数编码；
- `cross_entropy` 接收的是标准未归一化 logit，还是 CAM/概率式启发分数；
- 初始化来自缓存、原型或教师时，训练后是否还保留严格的检索/原型含义；
- 参数效率、训练效率和推理效率是否被混为一谈。

不要为了完成代码部分而运行完整训练。只有在单靠阅读无法确认shape或行为时，才考虑进行最小验证。

### 8. 选型指南

根据实际研究症状给出选择建议，例如：

| 当前问题 | 优先考虑 |
|---|---|
| …… | …… |

不要只写“方法A效果好，方法B计算贵”，而要说明：

- 什么情况下优先使用；
- 什么情况下不值得使用；
- 问题发生在语义侧还是空间侧；
- 是否真的需要训练新模块；
- 是否存在更简单的基线。

### 9. 论文和源码索引

保留简洁的导航区：

- 相关论文双链；
- 官方仓库；
- commit；
- 关键文件和函数；
- 每个链接解决什么问题。

目的是以后重新阅读时，不必再次从仓库根目录寻找入口。

### 10. 当前整理结论

总结当前已经能够确认的规律。

不要加入大段“以后还可以补充”的TODO清单。知识不需要一次穷尽，这篇笔记只负责及时整理当前已经理解的内容。

结论应该回答：

- 这个算子的核心选择是什么；
- 阅读新论文时应该追问什么；
- 修改模型时应该先检查什么；
- 不同论文的模块怎样放回同一条数据流中理解。

## 四、写作要求

1. 参考我现有论文笔记的风格：公式、张量变化、具体例子和“我的理解”提示块相结合。
2. 先直觉，后专业表达；先讲流程，后讲公式。
3. 面向可能已经忘记基础细节的自己写，不要省略关键中间步骤。
4. 语言清楚、简单、具体，避免为了显得专业而堆叠术语。
5. 每个展示公式都必须在紧邻位置使用 `**公式解释：**` 解释；公式声明、简单公式和总结框也不能省略。
6. 所有缩写第一次出现时必须展开。
7. 明确区分：
   - 论文声称什么；
   - 公式表达什么；
   - 代码实际上做什么；
   - 我的理解和判断是什么。
8. 不虚构源码路径、函数名、shape、实验结果或论文结论。
9. 如果代码仓库无法访问，要明确说明，不要根据论文公式假装已经阅读源码。
10. 不把笔记做成完整工程项目，不创建训练脚本、测试目录或复现项目。
11. 不以控制篇幅为主要目标，但避免重复解释同一件事。
12. 保持Markdown、LaTeX、YAML和Obsidian双链格式正确。
13. 张量 shape 建议统一使用反引号，例如 `[B,N,D]`；数学变量使用 `$...$`。不要出现用 `$` 开始却用反引号结束的混合标记。
14. 不要连续堆叠多个 `$$...$$` 后只写一段总解释；每个公式块单独解释。
15. 论文、公式、代码和“我的理解”必须明确区分，不能用自己的推断替代论文或源码事实。
16. 内容不能过少。每篇应足以独立回答“问题是什么、有哪些实现、张量怎样变化、如何选型、源码从哪里读”；但不要通过重复同一解释或大段复制论文来堆篇幅。
17. 第一次出现 CLIP、CAM、WSSS、OVS、SAM、EMA、LoRA、RFM 等缩写时，写出英文全称、中文含义和缩写；专有模型名称也要在首次出现时给出最低限度背景。
18. 修改已有参考页面时，若任务只要求补公式解释，则只调整公式附近内容，不改论文表格、源码分析、章节结构和原有结论。
