# 论文翻译与精读笔记生成规范（AI 工作流）

我会提供论文 PDF，可能还会提供补充材料、已有翻译或笔记、论文图片、官方代码仓库及相关基础笔记。请以论文原文为最高依据，在同一次任务中完成以下两个 Markdown 文件：

1. `{方法名}_Translation.md`：逐句、完整、客观的中文翻译；
2. `{方法名}_paper_notes.md`：以翻译文件为正文底稿、在对应位置插入理解性笔记的精读文件。

如果能够访问工作区，请直接创建或修改目标文件，不要把正文只回复在对话中，不要创建临时脚本、临时 Markdown 或无关目录。两份文件必须在同一次任务中完成，不要生成第一份后停止。

---

## 一、最终目标与核心原则

这不是生成两份互不相关的论文摘要。两个文件必须形成明确的上下游关系：

```text
论文 PDF / 补充材料
        ↓
完整、客观的 Translation
        ↓ 原文逐段复用
插入“我的理解” callout 的 paper notes
        ↓
关键实验、批判性判断与研究启发
```

必须遵守以下原则：

1. **原文与理解分离**：论文说了什么由正文翻译承担；怎样理解、怎样判断由 Obsidian callout 承担。
2. **先讲清主线，再补必要细节**：第一次解释框架或模块时，先说明输入、实际操作、输出及前后衔接，再解释公式、张量、梯度或实现细节。
3. **完整翻译与选择性精读分离**：`Translation.md` 保存全文；`paper_notes.md` 对 Method 之前完整保留，对 Method 之后进行有依据的筛选和分析。
4. **证据与推断分离**：明确区分论文明确陈述、补充材料说明、官方代码实现和个人分析，不得用常见做法补全作者没有说明的内容。
5. **面向以后重读**：笔记应让已经忘记论文细节的自己重新理解方法，而不是只堆叠术语、公式或逐段复述。

## 二、资料优先级与开始前检查

### 2.1 资料优先级

发生冲突时按以下顺序判断：

1. 论文正式版本 PDF；
2. 论文补充材料、附录和作者勘误；
3. 作者公开的官方代码及固定版本；
4. 作者项目页、README 或公开说明；
5. 已有翻译、手动笔记和二手资料。

已有笔记主要用于参考图片链接、文件路径、Obsidian 双链、章节排版和已经确认的解释。论文原文与已有笔记冲突时，以论文为准，并在理解性 note 中指出会影响方法理解的重要差异。

### 2.2 开始前必须检查

生成正文前先完成以下检查，但不要为检查过程创建额外文档：

- 确认论文标题、方法简称、发表 venue 和年份；
- 确认 PDF 是否包含附录或另有补充材料；
- 确认目标文件夹、目标文件名和本地 PDF 的相对路径；
- 搜索仓库中是否已有相关模型、基础机制或对比方法笔记；
- 检查已有图片链接能否复用，参考同目录论文的图片保存方式；
- 如果提供官方代码，确认它是否确实为作者仓库；需要引用实现事实时记录 commit；
- 记录无法辨认、无法访问或不同版本之间不一致的资料，不得猜测。

## 三、第一阶段：生成 `{方法名}_Translation.md`

### 3.1 翻译范围

逐句、完整、等义地翻译以下内容：

- 论文标题、摘要和关键词；
- 正文全部章节和小节；
- 公式及其正文说明；
- 图题、图注、图中可读文字；
- 表题、表头、表注、脚注、数值、单位和强调格式；
- 实验设置、主结果、消融、可视化、讨论和结论；
- 论文内附录及独立补充材料中的有效正文。

删除作者、机构、邮箱、基金、版权信息、页眉页脚、致谢和文末参考文献列表。正文中的引用编号必须保留。

不得总结、合并、删减、改写或补写原文。原文每个段落必须保持完整连续，不能被标题、图片、表格或额外解释插入段落中间。原文无法辨认时使用明确标记，例如“【原文此处无法辨认】”，不能根据上下文臆造。

### 3.2 图表处理

图表应按正文语义与阅读顺序放在相关完整段落之后，不机械照搬双栏 PDF 的版面顺序，也不得插入一个正文段落中间。

如果已有笔记包含正确的图片链接，必须原样保留。若没有，则从论文中提取图片，保存到仓库既有图片目录，并使用与同目录笔记一致的相对链接。实在无法取得图片时才使用独占一行的占位符：

```text
【图 1 插入位置】
```

每张图片统一采用：

```markdown
![](论文图片相对路径)

**图 1. 图题与图注的完整中文翻译。**

**图片内容解释：** 客观说明图中可见的输入、模块、箭头、文字、颜色编码、对比结果及其含义，不加入论文未表达的机制推断。
```

表格必须转换为完整 Markdown 表格，保留全部行列、数值、单位、脚注和强调格式。表题和表注放在表格前，表格前后各空一行。

### 3.3 公式规则

- 行内公式使用 `$...$`；
- 独立公式单独成行并使用 `$$...$$`；
- 保留原公式编号，使用 `\tag{n}`；
- 无编号公式不得擅自添加编号；
- 不使用 `\label{}`；
- 多字符下标、上标使用花括号，如 `$A_{ij}$`、`$A^{n-1}$`；
- 运算符和多字母缩写使用 `\mathrm{}` 或 `\text{}`；
- 多行公式使用 `\begin{aligned}...\end{aligned}`；
- 不改变变量、符号、运算顺序和数学含义；
- 公式内部不使用 Markdown 加粗或斜体语法。

### 3.4 Translation 的内容边界

`Translation.md` 只能包含：

- 论文的完整中文翻译；
- 客观的图片内容解释；
- 为保持排版而添加的必要 Markdown 标题。

严禁混入：

- `我的理解` callout；
- 方法评价、局限分析或研究启发；
- 论文未声明的张量 shape；
- 根据源码反推的实现说明；
- 对公式的教学式扩写；
- 额外摘要或章节总结。

## 四、第二阶段：生成 `{方法名}_paper_notes.md`

### 4.1 文件头与资源入口

文件开头使用 YAML Frontmatter。所有标签必须为英文小写并用短横线连接；不要把年份写入 tags。基础格式为：

```yaml
---
type: paper-note
tags:
  - cv
  - 具体任务
  - 监督方式
  - 核心基础模型
status: in-progress
model: 方法名
venue: 会议或期刊简称加年份
---
```

如果是弱监督语义分割，必须包含 `cv`、`semantic-segmentation`、`weakly-supervised` 和 `wsss`。`venue` 采用 `CVPR2026`、`ICCV2025`、`TIP2026` 等形式，不另设 `year` 字段。

YAML 后提供实际存在的资源入口：

```markdown
论文网址：[论文标题](URL)

代码：[作者/仓库名](URL)

本地 PDF：[方法名](相对路径)

相关笔记：[[基础模型]]｜[[最接近的方法]]
```

没有代码、补充材料或相关笔记时省略对应行，不写虚假的占位链接。

#### DiCLIP 风格示例

```yaml
---
type: paper-note
tags:
  - cv
  - semantic-segmentation
  - weakly-supervised
  - clip
  - stable-diffusion
  - wsss
status: done
model: DiCLIP
venue: TIP2026
---
```

这个例子说明字段和标签粒度，不代表所有论文都要使用 WSSS、CLIP 或 Stable Diffusion 标签。

### 4.2 正文与 Translation 的复用关系

`paper_notes.md` 必须以已经完成的 `Translation.md` 为底稿：

- 从论文标题、摘要、Introduction、Related Work 到 Method / Approach / Framework 结束，完整复制对应译文、标题、公式、图片和表格；
- 不得改写、删减、合并、概括或移动原文段落；
- 理解内容只能插入在相关完整段落、公式、图片或表格之后；
- 不得用 callout 打断一个原文段落；
- Method 之后可以只保留关键实验、主要消融、重要讨论、结论与局限，因为完整内容已经保存在 `Translation.md`。

如果论文没有标准的 Introduction、Related Work 或 Method 标题，按照其真实结构识别“研究背景结束位置”和“方法主体结束位置”，不得为了套模板而重命名或重排原文章节。

## 五、理解性 note 的统一格式与写作顺序

所有个人解释统一使用：

```markdown
> [!note] 我的理解｜简短而具体的标题
> 内容……
```

不要使用“原文翻译到这里结束”“下面解释公式”“问：……答：……”等模板化话术。标题应指出 note 真正回答的问题，例如：

- `我的理解｜整体流程与梯度边界`
- `我的理解｜缓存检索为什么像注意力，又和注意力不完全一样？`
- `我的理解｜从离线视觉词典到可训练 patch 分类器`
- `我的理解｜能力边界：两条前提会把误差带进伪标签`

### 5.1 Introduction 和 Related Work：只建立坐标系

只添加少量必要 note，用于回答：

- 本文究竟解决哪个任务设定；
- 主流范式是什么，瓶颈具体发生在哪里；
- 本文改变的是监督来源、模型结构、数据流还是优化方式；
- 它与最接近工作的真正区别是什么；
- 阅读后文前必须理解的基础概念是什么。

不要逐段扩写，不要提前解释尚未出现的全部公式与模块。

#### DiCLIP 风格示例

当原文比较“图像—文本对齐”和“patch—文本对齐”时，合格 note 不应只说后者更细粒度，而应说明**空间响应从哪里来**：前者从全局匹配分数的梯度或区域约束恢复位置，后者直接计算每个 patch 与类别文本的相似度。随后指出两者仍共同受 CLIP 图像级预训练目标限制。这个例子体现的是“先建立研究坐标”，不是要求照抄 DiCLIP 的结论。

### 5.2 Method 开始：先写整体流程

优先在总体框架图及其原文说明之后加入“整体流程” note。严格按前向顺序解释：

1. 输入图像、文本、标签、提示或支持样本分别是什么；
2. 哪些预训练模型冻结，哪些模块需要学习；
3. 数据依次经过哪些阶段；
4. 每个阶段产生什么中间结果并交给谁；
5. 最终预测、CAM、伪标签或其他输出怎样产生；
6. 每个 loss 使用什么预测和标签；
7. 训练阶段与推理阶段保留哪些组件；
8. 离线预处理、在线训练和测试时操作是否被论文混用。

整体流程只负责建立主线，不在这里穷举所有 shape、超参数和源码细节。

#### DiCLIP 风格示例

DiCLIP 的整体 note 应先说明：SD 在离线阶段提供空间关系并生成单类图像；这些信息用于增强 CLIP 特征并构建键值缓存；在线训练阶段由静态缓存监督动态适配器，动态伪标签再监督分割头；最终推理只保留冻结 CLIP 特征和分割头。只有在主线明确后，才继续分析 Kmeans、PAR、两层适配器和梯度边界。

### 5.3 核心模块：解释它本质上做了什么

每个核心模块按以下顺序解释：

1. **目的**：它修复哪一种明确错误；
2. **输入**：接收特征、概率、关系矩阵、掩码、原型还是标签；
3. **实际操作**：按顺序描述真正发生的数值操作；
4. **输出**：产生什么对象，shape 是否改变；
5. **前后衔接**：输出交给哪个模块或 loss；
6. **参数状态**：可学习、冻结、无参数、离散、停止梯度或 EMA 更新；
7. **设计意义**：为什么该操作可能解决前述问题；
8. **能力边界**：它依赖什么前提，错误可能怎样传播。

解释聚类时必须说明是在聚类像素特征、patch 特征、原型还是关系向量；解释 attention 时必须说明矩阵元素代表谁对谁的权重；解释缓存时必须说明 key、value 和 query 分别保存什么。不要只复述作者给模块起的名称。

### 5.4 关键公式：先说整体作用，再解释细节

只对理解方法主流程有帮助的关键公式加入 note。按照以下顺序：

1. 一句话说明公式整体在计算什么；
2. 说明主要符号、计算顺序和输出含义；
3. 补充必要的输入输出 shape；
4. 说明矩阵乘法消去哪个维度，或说明它只是逐元素操作；
5. 说明 softmax、mean、max、sum、归一化在哪个维度发生；
6. 解释权重、阈值和超参数的作用；
7. 必要时给一个很小的数字例子；
8. 区分通用数学操作与作者提出的新设计。

不要连续堆叠多个公式后只写一次总解释，也不要为每个显而易见的 shape 声明添加冗长推导。完整源码级尺寸变化留给 code note，除非该变化会影响论文机制的正确理解。

#### DiCLIP 公式与 note 配对示例

原文公式应首先保持原样：

$$
M_d=\sigma\left(P_eW_1^T+b_1\right)W_2+b_2.
$$

随后在 `paper_notes.md` 中插入类似以下结构的解释：

```markdown
> [!note] 我的理解｜从离线视觉词典到可训练 patch 分类器
> 固定缓存原本执行“patch 查询视觉键，再由值完成类别投票”。把键和值分别看成两层线性权重后，这个检索过程与一个两层网络同形。缓存只负责初始化；训练开始后，权重会根据真实图像调整，因此它不再是严格的最近邻检索，而是由缓存初始化的 patch 分类器。
>
> 若 $P_e\in\mathbb R^{HW\times D}$、$W_1\in\mathbb R^{U'\times D}$、$W_2\in\mathbb R^{U'\times C}$，则第一步消去特征维 $D$，得到每个 patch 对 $U'$ 个原型槽位的响应；第二步消去槽位维 $U'$，得到 $HW\times C$ 的类别响应。
```

这个例子体现三点：先解释“它在做什么”，再给必要 shape，最后指出训练会改变“检索”这一语义。不要把例子中的符号强行用于其他论文。

### 5.5 多个 loss：用“谁教谁”理清监督链

当论文包含多个 loss 时，必须说明：

- 每个 loss 的预测量和监督标签；
- 它主要更新哪些模块；
- 标签或伪标签从哪里来；
- 梯度是否跨越教师、冻结骨干或其他分支；
- 哪些阈值选择、argmax、聚类、伪标签或缓存状态不参与反向传播；
- 辅助 loss 在推理时是否仍需要。

先用简单语言写清监督关系，再补梯度边界。

#### DiCLIP 风格示例

```markdown
> [!note] 我的理解｜两个 loss 怎样串起两级“老师带学生”？
> 静态缓存生成伪标签，首先监督动态适配器；动态适配器产生的 CAM 经细化后，再监督最终分割头。SD、冻结 CLIP、Kmeans、离散伪标签和空间细化不是端到端更新对象。总损失只是同时训练两个学生，不代表出现了第三种监督信号。
```

### 5.6 能力边界与批判性判断

在主流程解释清楚以后，加入少量独立 note 分析：

- 方法依赖的关键假设是否始终成立；
- 不同模块是否来自同一个可能犯错的信息源；
- 伪标签、自训练或检索是否形成确认偏差；
- 背景、未知类、ignore 和 no-object 是否被混为一谈；
- 训练、推理、离线预处理和测试时优化的开销分别是什么；
- 所谓 training-free、parameter-efficient 或 real-time 的边界是什么；
- 在小目标、遮挡、长尾、域偏移或类别共现下可能怎样失败；
- 论文实验是否真正验证了所声称的机制，而不只是最终指标提高。

批判不能先于机制理解，也不能把未经验证的猜测写成事实。使用“可能”“从公式看”“论文没有说明”“官方代码显示”等准确措辞标明证据强度。

## 六、Method 之后：实验、结论与研究判断

`paper_notes.md` 不必复制全部实验，但必须保留足以支持或质疑论文主张的证据。

### 6.1 应保留的实验内容

- 数据集、监督设定和主要评价指标；
- 与最相关方法的核心结果；
- 直接验证主要模块的消融；
- 计算量、参数量、训练成本和推理成本；
- 能暴露成功或失败模式的定性结果；
- 作者明确承认的局限；
- 与论文主要主张直接相关的补充实验。

### 6.2 实验 note 应回答的问题

- 比较是否使用相同骨干、额外数据、分辨率和后处理；
- 改进来自本文核心机制，还是来自更强基础模型或更多数据；
- 消融是否一次只改变一个因素；
- 提升发生在最终分割、CAM、伪标签还是某个代理指标；
- 是否报告方差、多个 seed 或统计显著性；
- 效率结论是否把离线预处理排除在外；
- 是否存在只对特定类别、尺度或数据集有效的迹象。

### 6.3 结尾建议结构

在不重复摘要的前提下，用简洁的个人总结结束：

```markdown
## 总结与研究启发

### 这篇论文真正改变了什么

### 最值得保留的机制

### 局限与未验证假设

### 与现有笔记或研究方向的连接

### 一个最小可证伪实验
```

只填写确实能从论文、代码或已有研究问题中推出的内容。不要生成空泛的“未来可以进一步提升性能”。“最小可证伪实验”应明确改变一个变量、观察一个指标，用来检验论文最重要的因果主张。

## 七、官方代码的使用边界

`paper_notes.md` 以论文机制理解为主，不写成源码逐行分析。官方代码只用于核对会影响主流程的事实，例如：

- 哪些骨干冻结、哪些参数加入优化器；
- 某个伪标签或教师输出是否 `detach`；
- 训练与推理实际保留哪些模块；
- 背景、unknown、ignore 和 no-object 的通道定义；
- 论文公式与实现是否存在会改变结论的重要差异；
- 论文未给出的关键 shape 是否能从源码确定。

引用源码事实时，应记录完整 commit、文件路径、类或函数，优先使用固定到 commit 和行号的 GitHub 链接。仓库无法访问时明确写“未完成源码核对”，不得虚构路径、函数、shape 或训练行为。

大段调用链、逐行代码、完整张量追踪和环境运行过程应单独写入 `{方法名}_code_notes.md`，不塞入论文笔记。

## 八、Markdown、语言与 Obsidian 规范

- 全部使用中文简体，必要的模型名、缩写、数据集名和专有名词保留英文；
- 缩写第一次出现时给出英文全称、中文含义和缩写；
- 使用论文原有章节结构和合理的 Markdown 标题层级；
- 正文段落之间空一行；
- 表格、公式块、图片及 callout 前后保留空行；
- 张量 shape 推荐使用反引号，如 `[B,N,D]`；数学变量使用 `$...$`；
- 不混用 `$` 与反引号；
- Obsidian 双链只指向仓库中实际存在或本次创建的笔记；
- 普通外部网址和相对文件路径使用 Markdown 链接；
- 图片必须来自论文、补充材料或论文官方项目页，不用无关示意图替代；
- 不把两个文件包进代码围栏；
- 不在文件正文之外加入“以下是生成结果”等对话式前言。

## 九、禁止事项与异常处理

### 9.1 禁止事项

- 不把 `paper_notes.md` 写成脱离原文的摘要；
- 不把 `Translation.md` 写成解释性笔记；
- 不静默修改论文公式、数值或实验结论；
- 不为迎合模板重排、重命名论文原有章节；
- 不在每个段落后机械添加 note；
- 不反复解释同一条流程；
- 不一开始就堆叠完整 shape、梯度图或源码差异；
- 不把前向箭头自动解释成可反向传播；
- 不把冻结模型、无参数操作和停止梯度操作混为一类；
- 不把“无需额外训练”“参数高效”“测试时优化”都称为 training-free；
- 不虚构论文、源码、链接、图片、shape、参数量或实验结果；
- 不运行完整训练来填充论文笔记，除非用户另行要求复现；
- 不修改任务范围之外的现有笔记。

### 9.2 异常处理

- **PDF 无法读取**：报告具体无法读取的文件或页码，不用二手资料代替全文；
- **公式疑似排版错误**：保留译文中的原公式，在相邻 note 中说明疑点及核对依据；
- **论文与补充材料冲突**：标明版本与位置，优先采用作者更新版本；
- **论文与代码冲突**：正文保持论文说法，note 中说明官方代码实际行为及 commit；
- **图片无法提取**：使用明确占位符，不生成臆造图片；
- **代码仓库不可访问**：省略源码结论并明确未核对；
- **目标文件已有内容**：保留正确的图片链接、人工批注和未被新证据否定的内容，避免无理由覆盖；
- **资料不足以完成两份文件**：明确阻塞项，不把不完整结果描述为已完成。

## 十、执行顺序

严格按照以下顺序完成任务：

1. 读取目标目录、模板、论文 PDF、补充材料和已有笔记；
2. 确认元数据、资源链接、图片路径和论文真实结构；
3. 完成并保存整个 `{方法名}_Translation.md`；
4. 检查翻译是否覆盖实验、附录、公式、图表和脚注；
5. 创建 `{方法名}_paper_notes.md` 的 YAML 与资源入口；
6. 从 Translation 复制标题到 Method 结束的完整正文；
7. 先加入少量背景坐标 note，再加入整体流程 note；
8. 按模块、公式、监督链和能力边界插入理解性 note；
9. 从 Translation 选择关键实验、消融、结论和局限；
10. 添加基于证据的总结、研究连接和最小可证伪实验；
11. 核对两个文件的一致性和所有链接；
12. 执行格式、范围和工作区 diff 检查；
13. 两份文件均完整后再统一汇报，不在中途停止。

## 十一、完成后的强制检查

### 11.1 Translation 检查

- [ ] 标题、摘要、关键词、全部正文、实验、结论和附录均已翻译；
- [ ] 所有公式、编号、变量和数学关系与原文一致；
- [ ] 所有图题、图注、表格、脚注和单位完整；
- [ ] 图片链接有效，图片没有插入段落中间；
- [ ] 只包含客观翻译与图片说明；
- [ ] 没有“我的理解”、评价、源码分析或额外总结；
- [ ] 没有作者信息、致谢和文末参考文献列表。

### 11.2 paper notes 检查

- [ ] YAML 的 type、tags、status、model、venue 合法；
- [ ] 论文网址、本地 PDF、代码和相关笔记链接真实有效；
- [ ] 从标题到 Method 结束完整复用了 Translation；
- [ ] 原文段落没有被改写、删减、合并、移动或打断；
- [ ] Introduction 和 Related Work 没有被过度扩写；
- [ ] 框架图后已经先说明整体前向流程；
- [ ] 每个核心模块都说明输入、操作、输出和前后衔接；
- [ ] 关键公式先有直觉，再有必要符号、shape 和小例子；
- [ ] 多个 loss 已按“谁教谁”说明监督对象与梯度边界；
- [ ] 已区分可学习、冻结、无参数、离散、停止梯度和非梯度状态；
- [ ] 已说明训练、推理、离线预处理和测试时操作的差异；
- [ ] Method 之后保留的实验足以支持主要研究判断；
- [ ] 批判性内容标明证据强度，没有把推断写成事实；
- [ ] 没有与单独 code note 重复的大段源码分析。

### 11.3 格式与范围检查

- [ ] `$$`、反引号、代码围栏和 YAML 分隔符成对；
- [ ] LaTeX 命令的反斜杠完整；
- [ ] 表格列数一致，公式块和表格前后有空行；
- [ ] Obsidian 双链目标真实存在；
- [ ] 图片和 PDF 相对路径能够从目标文件解析；
- [ ] 两个文件中的公式编号、图片链接和章节顺序一致；
- [ ] 已查看实际 diff，只修改了任务范围内的目标文件；
- [ ] 已运行 `git diff --check` 或等价空白检查。

## 十二、完成后的汇报格式

两份文件都完成并检查后，简洁汇报：

- 创建或修改的文件；
- Translation 覆盖的论文范围，是否包含附录；
- paper notes 新增的主要理解内容；
- 复用了哪些已有图片和相关笔记；
- 是否核对官方代码；若核对，给出仓库与 commit；
- 是否运行代码或训练；
- 公式、图片、表格、双链、LaTeX 与 `git diff --check` 的验证结果；
- 是否只修改任务范围内文件；
- 工作区原本存在但本轮未触碰的其他未提交修改。

如果任一必需检查失败，必须如实报告具体问题，不得声称两份文件已经完整完成。
